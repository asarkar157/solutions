Skill: Branch + commit + push + open a PR for the newly scaffolded scenario, then comment back on the originating issue. This skill assumes `scenario-scaffold-sop` already ran and left files staged in the working tree at `<repo_clone_path>`.

Keywords for skill discovery: pull request, gh pr create, gh issue comment, git push, branch, scenario-bot, scaffold pr, scenario-request, issue comment.

Prerequisites (all from notes):
- `repo_clone_path` — clone with scaffolded files in the working tree.
- `scenario_slug` — used in branch name + PR title.
- `validation_summary` — `ok: ...` or `failed: ...`.
- `scaffold_summary` — file list + module list for the PR body.
- `gh_token`, `repository_full_name`, `issue_or_pr_number`, `repository_default_branch` — for `gh pr create` and `gh issue comment`.
- `issue_details.title` — quoted in the PR body.

Tool boundary: every command here runs in the Ubuntu CLI sandbox via the `scaffold-pr` subagent (orchestration SOP Template D) followed by the `notify-issue-comment` subagent (Template E).

========================================================================
0) Bootstrap — ensure `gh` and `git` are on PATH
========================================================================

Templates B and C should have already installed `gh`, `git`, and `tofu`/`terraform` in this sandbox. But subagent sandboxes are not guaranteed to share state, so re-assert:

a) `export PATH="$HOME/.local/bin:$PATH"`.
b) `which gh && which git` — both must succeed. If either is missing, re-run the matching install step from orchestration-sop Template B step 0 (the apt + tarball fallbacks). On failure, persist `bootstrap_blocker="gh_missing"` or `"git_missing"` and STOP (orchestration §6(f)). NEVER attempt a `git push` without a working `gh` (the push uses the gh-installed credential helper).

========================================================================
1) Create the working branch
========================================================================

Inside `<repo_clone_path>` (run as a single `execute_series` so the env survives):

  `export GH_TOKEN=<gh_token> && export GITHUB_TOKEN=$GH_TOKEN && gh auth setup-git || true`
  `git fetch origin <repository_default_branch>`
  `git switch <repository_default_branch>`
  `BRANCH="scenario-bot/<scenario_slug>-$(date +%Y%m%d%H%M%S)" && git switch -c "$BRANCH"`
  note key="working_branch", value="$BRANCH"

If `git switch -c` fails (branch already exists from a prior failed run), append `-retry` and try once.

========================================================================
2) Commit the scaffold
========================================================================

a) Read notes `scaffold_blocker:*` to learn which files the scaffold subagent ACTUALLY managed to write. Build the stage list dynamically — never blindly assume all three paths are present:

      `STAGE_PATHS="examples/scenarios/<scenario_slug>/"`
      `if [ -z "$scaffold_blocker_demo_sh" ]; then STAGE_PATHS="$STAGE_PATHS scripts/demo.sh"; fi`
      `if [ -z "$scaffold_blocker_playbook" ]; then STAGE_PATHS="$STAGE_PATHS docs/se-playbook.md"; fi`

   (Replace the boolean checks with whatever shape `scaffold_blocker:*` ended up as in your notes — the principle is: stage only the paths the scaffold subagent successfully wrote.)
b) `git add $STAGE_PATHS`
c) `git status --porcelain` → confirm ONLY the planned files are staged. Forbidden additions: anything outside the three stage paths above. If anything else is staged (e.g. accidental edits to other modules or root files), `git reset` those files and re-stage just the allowed set. NEVER push a commit that touches `modules/`, `examples/complete/`, root files, CI config, or pre-commit hooks.
d) `git commit -m "scenario(<scenario_slug>): scaffold from issue #<issue_or_pr_number>"` — keep the subject line ≤ 72 chars.

If `git commit` says "nothing to commit", the scaffold subagent did not write files. note `pr_blocker="empty_commit"`, STOP, and let the planner branch to §6 (blocked notification).

========================================================================
3) Push + open the PR
========================================================================

  `git push -u origin "$BRANCH"`

If push is rejected because the branch was force-pushed elsewhere, do NOT force-push back — branch to §6 and let humans investigate.

PR title:
  - Happy path: `scenario(<scenario_slug>): from #<issue_or_pr_number>`
  - Validation failed: `[draft] scenario(<scenario_slug>): from #<issue_or_pr_number> — validation failed`

PR body (heredoc so multi-line markdown survives — replace placeholders with values from notes; conditional sections are inserted only when the matching note is non-empty):

```md
## Summary

Generated by the scenario-author bot from #<issue_or_pr_number>:
"<issue_details.title>".

Pitch (from the original issue):

> <pitch_quote>

## What this PR adds

- `examples/scenarios/<scenario_slug>/` — new runnable scenario root (main.tf, variables.tf, outputs.tf, terraform.tfvars.example, README.md).
<if scripts/demo.sh staged> - One new case in `scripts/demo.sh scenario_pitch()` so `make demo-list` picks up the new pitch.
<if docs/se-playbook.md staged> - One new row in `docs/se-playbook.md` "Prospect-question → scenario" table.

## Modules wired

<bullet list extracted from scaffold_summary.modules_wired>

## Integrations branched

<scaffold_summary.integrations_branched formatted as `aws (required)`, `slack (optional)`, `grafana (skipped)`, etc.>

## Validation

`<scaffold_summary.iac_binary>`: `<validation_summary verbatim>`

## Reviewer checklist

- [ ] `make demo SCENARIO=<scenario_slug>` runs end-to-end against a real tenant
- [ ] Talk track in the README matches the original issue
- [ ] Assign the scenario to an owner in `CONTRIBUTORS-SE.md`
<if unknown_modules non-empty> - [ ] Resolve unknown modules referenced in the issue: <comma-separated unknown_modules>. Bot left them out — please add them under `modules/` or correct the names in the issue body and re-run.
<if scaffold_blocker:demo_sh_corrupted set> - [ ] Append the `<scenario_slug>` case to `scripts/demo.sh scenario_pitch()` manually (bot's splice attempts corrupted the file).
<if scaffold_blocker:playbook_corrupted set> - [ ] Append a row to the `docs/se-playbook.md` "Prospect-question → scenario" table manually (bot's splice attempts corrupted the file).
<if module_signatures.extra_required emitted any TODOs> - [ ] Fill in the per-module required vars marked `# TODO:` in `main.tf` and re-run `tofu validate`.

Closes #<issue_or_pr_number> when merged.
```

Open the PR (heredoc-fed `--body-file -`):

```
gh pr create \
  --repo <repository_full_name> \
  --base <repository_default_branch> \
  --head "$BRANCH" \
  --title "<title from above>" \
  --label scenario-request \
  --body-file - <<'EOF'
<body from above>
EOF
```

Add the `[draft]` flag (`--draft`) only when `validation_summary` starts with `failed:`. NEVER force a PR when push or `gh pr create` fails with a non-recoverable error — branch to §6 instead.

Capture the URL:
  `gh pr view --repo <repository_full_name> "$BRANCH" --json url -q .url`
  note key="pr_url", value="<URL>"

========================================================================
4) Persist stage summary
========================================================================

note key="stage_summary:scaffold-validate-pr", value=<one paragraph: branch, PR URL, validation outcome, files touched>.

This stage is now complete. The planner moves to `notify-issue-comment` (Template E) which posts the final issue comment.

========================================================================
5) Comment back on the originating issue (handled by Template E)
========================================================================

Template E branches on the captured notes to pick one of:

a) Existing-match path — `existing_match` is non-null. Body:

```md
## Existing scenario match

I think `<existing_match.name>` already covers this. Rationale:
<existing_match.rationale>

Run it now:
```bash
<existing_match.run_command>
```

README: <repo_url>/blob/<repository_default_branch>/<existing_match.readme_path>

If this is wrong, comment with `not-a-match` and re-open / re-label — I will
re-triage on the next event.
```

b) Happy-path PR — `pr_url` is non-empty, validation passed. Body:

```md
## Scaffolded a PR

Branch: `<working_branch>`
PR: <pr_url>
Validation: <validation_summary>

## What's in the PR

- `examples/scenarios/<scenario_slug>/main.tf|variables.tf|outputs.tf|terraform.tfvars.example|README.md`
- `scripts/demo.sh` — new `<scenario_slug>` entry so `make demo-list` shows the pitch.

Reviewer: please run `make demo SCENARIO=<scenario_slug>` against a clean
tenant once you wire your credentials in `terraform.tfvars`.
```

c) Draft-PR path — `pr_url` non-empty, validation failed. Body:

```md
## Scaffolded a draft PR (validation failed)

Branch: `<working_branch>`
PR (draft): <pr_url>
Validation: `<validation_summary>`

A scenario owner from `CONTRIBUTORS-SE.md` should review the validation
error and fix the scaffold before un-drafting. The PR body has the full
reviewer checklist. The bot does not have an ownership map, so it cannot
@-mention the right person here — please assign manually.
```

d) Blocked path — any `stage_summary:*` begins with `blocked:`. Body:

```md
## Workflow blocked

The scenario-author bot could not finish this request. Blocker:

> <quoted stage_summary text>

<if unknown_modules non-empty>Modules the bot did not recognize from the issue body: `<comma-separated unknown_modules>`. Either correct the names (see `modules/aios-*/` for valid names) or wait for the modules to land, then re-open this issue.

Recovery: see `docs/se-feedback.md` and re-open this issue once the blocker
is fixed. The bot will re-triage when the next `issue.created` /
`issues.opened` / `issues.labeled` event fires (close + re-open with the
`scenario-request` label is the simplest way).
```

e) Budget-exhausted path — any `stage_summary:*` value contains "budget" (case-insensitive) AND `pr_url` is empty. Body:

```md
## Budget exhausted

The scenario-author bot ran out of its daily budget cap before it could
finish triaging this request. The cap resets at the next UTC day boundary.

Recovery (any one of):

1. Wait for the daily reset, then re-open / re-label this issue (the bot
   re-triages on the next `issue.created` / `issues.labeled` event).
2. Ask the operator to raise `agent_budget` on the
   `aios-agent-scenario-author` module instance if this happens repeatedly.
3. Skip the bot — a scenario owner from `CONTRIBUTORS-SE.md` can scaffold
   manually using `examples/scenarios/aws-sre-demo/` as a template.

Originating stage: `<stage_id quoted from stage_summary>`.
```

f) "Triaged, no action taken" — fallback when no other branch matched. Body:

```md
## Triaged, no action taken

The scenario-author bot reached this issue but did not produce a PR, find
an existing match, or report a clear blocker. This usually means the bot
yielded mid-stage (transient model error or sandbox issue).

Recovery: close and re-open this issue (the bot re-triages on the next
`issue.created` event) or wait — the workflow will fire again on any
future event. If this is the second consecutive "no action taken" reply,
please ping the engineering lead in `#aios-modules-se`.
```

Choose exactly ONE body and call `gh issue comment <issue_or_pr_number> --repo <repository_full_name> --body-file - <<'EOF' ... EOF`. After the comment, note `stage_summary:notify` with the comment kind chosen and the issue URL.

Forbidden:
- Posting the token, the `gh_token` note value, or any other secret in any comment.
- Sending more than one comment per workflow run (Template E runs at most once).
- Force-pushing the working branch or pushing to `<repository_default_branch>` directly.
- Triggering yet another `gh pr create` after `pr_url` is already populated.
